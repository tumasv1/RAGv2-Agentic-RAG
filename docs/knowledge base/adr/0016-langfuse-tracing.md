## ADR-0016: Трейсинг LLM-запросов через self-hosted Langfuse

**Статус:** принято

**Дата:** 07.07.26

---

## Контекст

После [[0014-llm-gateway]] и [[0015-prometheus-grafana-monitoring]] появились
агрегированные метрики (расходы, latency, fallback), но ни то, ни другое не
отвечает на вопрос **«что именно произошло в конкретном запросе»**:

- Grafana показывает, что запрос занял 8 секунд и стоил $0.002, но не
  показывает сам промпт, ответ, какие инструменты вызвал агент и в каком
  порядке — для отладки конкретного «странного» ответа приходится читать
  логи контейнера вручную
- У RAGv2 ReAct-цикл (`agent → tools → generate`, до 5 итераций) — интересно
  видеть его как дерево, а не как плоский список HTTP-вызовов к шлюзу
- Шлюз — общая инфраструктура для нескольких LLM-инструментов пользователя
  (RAGv2, OpenClaw и др.); нужно видеть трафик каждого клиента отдельно, не
  только RAGv2

Вопрос — не «нужен ли трейсинг», а «какой инструмент и где его разместить»,
учитывая, что в промптах/ответах RAGv2 может быть личный контент из Obsidian
vault (заметки, дневник, здоровье, финансы — см. структуру vault в
`CLAUDE.md`).

---

## Варианты

**Вариант А: Ничего не делать, хватает Grafana**

- Плюсы: ноль новой инфраструктуры
- Минусы: агрегированные метрики не показывают содержимое конкретного
  запроса — ту самую информацию, которая обычно и нужна при отладке
  «агент ответил не то»

**Вариант Б: LangSmith (SaaS от LangChain)**

- Плюсы: нулевая инфраструктура, готовая интеграция с LangGraph
- Минусы: облачный сервис — промпты и ответы (потенциально личный контент
  из vault) уходят на сторонние сервера; платный тариф при заметном объёме
  трафика

**Вариант В: Self-hosted Langfuse (принято)**

Открытый трейсинг-платформа с self-host режимом; стек v3
(web + worker + ClickHouse + Postgres + Redis + MinIO).

- Плюсы: данные не покидают домашнюю сеть; интеграция с LangChain/LangGraph
  из коробки (`langfuse.langchain.CallbackHandler`) — видит дерево ReAct без
  доп. кода; LiteLLM умеет писать трейсы напрямую (`success_callback:
  ["langfuse"]`) — второй источник почти бесплатно; UI с фильтрами по
  сессии/тегу/окружению/стоимости
- Минусы: тяжёлый стек (ClickHouse — главный потребитель RAM), нужен
  отдельный LXC; ещё одна система с бэкапами/эксплуатацией

**Вариант Г: Свой лог промптов/ответов (файл или таблица в SQLite)**

- Плюсы: полный контроль, ничего стороннего
- Минусы: изобретение велосипеда — нет UI, нет группировки по сессиям/тегам,
  нет расчёта стоимости по токенам, нет дерева вызовов

---

## Решение

Выбираем **Вариант В**: self-hosted Langfuse v3, отдельный проект
`/Users/mikhail/Projects/Langfuse`, свой LXC `192.168.3.204:3000`.

**Отдельный LXC**, не общий с шлюзом или Prometheus/Grafana — ClickHouse
заметно тяжелее по RAM, чем остальная инфраструктура, изоляция снижает риск
конкуренции за память с критичными сервисами (шлюз обслуживает весь LLM-трафик
пользователя).

**Два источника трейсов пишут в один проект `ragv2`:**

1. Шлюз — `success_callback: ["langfuse"]` в `litellm_config.yaml`. Видит
   вызовы всех клиентов шлюза (не только RAGv2), но плоско — без структуры
   ReAct-цикла.
2. Граф RAGv2 — `langfuse.langchain.CallbackHandler`, подключается в
   `agent/graph.py::_get_langfuse_handler()`. Видит полное дерево одного
   диалога (`agent → tools → generate`), потому что цепляется к LangGraph, а
   не к HTTP-вызову.

**Объединение в один трейс.** Изначально оба источника писали независимо —
один вопрос агенту порождал два трейса, а стоимость вызова считалась дважды
(дерево графа + отдельная плоская запись шлюза). Решение: `ask()`/`ask_debug()`
оборачивают граф в корневой спан Langfuse (`_langfuse_span`,
`start_as_current_observation` — API v4), а ноды графа передают его trace_id
в шлюз через `extra_body.metadata.existing_trace_id`
(`core/llm_client.py::get_langfuse_extra_body()`). Генерация LiteLLM ложится
в тот же трейс, что и дерево графа — виден и ReAct-путь, и реальный
`api_base` провайдера (для проверки fallback) в одном месте.

**Доработки читаемости** (по итогам первого дня использования):
- `session_id` = `thread_id` сессии (через `propagate_attributes`) — диалоги
  из нескольких вопросов группируются во вкладке Sessions
- Имя и `input`/`output` трейса — из вопроса и ответа агента (а не
  фиксированное имя и системный промпт на 14 КБ)
- `LANGFUSE_TRACING_ENVIRONMENT` (`production`/`development`) — локальные
  прогоны не портят прод-статистику
- Тег `RAGv2` на трейсе ставит сам граф (`propagate_attributes(tags=...)`),
  **не** `langfuse_default_tags` шлюза — раз граф теперь владеет трейсом
  (создаёт его первым), только владелец может проставить трейсу тег; шлюз,
  пристёгивающий генерацию через `existing_trace_id`, этого сделать не может
  (проверено эмпирически: шлюз присылал `tags:["RAGv2"]` в metadata запроса,
  но итоговый `tags` трейса оставался пустым, пока тег не стал ставить сам
  граф)
- Для остальных клиентов шлюза (которые трейс не объединяют, например
  OpenClaw) `langfuse_default_tags: [user_api_key_alias, cache_hit]`
  по-прежнему работает как задумано — тег ставится при создании трейса,
  которым в этом случае владеет сам шлюз

Полный план дальнейших улучшений (сегментация title/eval-вызовов, перевод
RAGAS-судьи через шлюз) — `docs/knowledge base/description/langfuse-tracing-improvements.md`
(локальный файл, не в git — содержит рабочие детали анализа, не архитектурное
решение).

## Последствия

- Отладка конкретного ответа агента теперь не требует чтения логов контейнера
  — открыл трейс в UI, увидел весь путь: вопрос → промпт → инструменты →
  ответ, с таймингами и стоимостью на каждом шаге
- Личные данные (вопросы пользователя, содержимое найденных заметок из vault,
  ответы агента) теперь хранятся в ClickHouse на `192.168.3.204` — не
  покидают домашнюю сеть, но это дополнительное хранилище персональных
  данных, требующее того же уровня доверия, что и сам Obsidian vault
- Третий отдельный LXC для observability-инфраструктуры (после шлюза и
  Prometheus/Grafana) — больше поверхность для эксплуатации (апдейты,
  бэкапы, RAM). Retention для ClickHouse (Settings → Data Retention в UI
  Langfuse) пока не настроен — трейсы копятся неограниченно
- Трейсинг рассчитан как **опциональный слой**: `langfuse.enabled: false` в
  `config.yaml` (или отсутствие ключей) полностью отключает
  CallbackHandler/спан — граф и шлюз работают как раньше, поведение не
  меняется. Специальной проверки поведения при недоступном Langfuse LXC
  (сеть/перезагрузка) под нагрузкой не проводилось — SDK шлёт трейсы
  асинхронно батчами, не должно блокировать сам запрос, но это допущение, а
  не проверенный факт
- RAM на всех трёх LXC (шлюз, Prometheus/Grafana, Langfuse) в процессе
  эксплуатации пришлось поднимать выше первоначальной оценки — стартовые
  всплески памяти (миграции БД, инициализация ClickHouse) недооценивались;
  подробности в `docs/knowledge base/description/monitoring.md`
- Следующий шаг — пункт 6 плана улучшений: отдельные virtual keys для
  служебных вызовов (`generate_title`, RAGAS eval), чтобы не путались с
  ответами агента в фильтрах Langfuse, и перевод RAGAS-судьи через шлюз (его
  расходы сейчас нигде не видны — ни в LiteLLM, ни в Langfuse, ни в Grafana)
