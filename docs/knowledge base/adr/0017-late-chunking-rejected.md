## ADR-0017: Local Late Chunking — эксперимент проведён, решение отклонено

**Статус:** принято (решение — не внедрять)

**Дата:** 10.07.26

---

## Контекст

Текущая Parent-Child схема (ADR-0010): child-чанки (800/300) ищутся, parent-чанки (2000/200) отдаются LLM. Children эмбеддятся независимо друг от друга — attention модели не выходит за границы одного child'а, поэтому смысловые связи внутри секции/parent'а (анафоры, «этот проект», «с кем был разговор») могут теряться при векторизации отдельного маленького куска, если сам он их не содержит явно.

Гипотеза: Late Chunking (Jina AI) — сначала эмбеддим более широкий контекст целиком, потом усредняем токен-векторы по границам чанков — child получает вектор, «знающий» соседей через двунаправленный attention, без изменения самих границ чанков.

Полный план эксперимента, включая исследовательскую часть (замеры jina-embeddings-v3), — [late-chunking-experiment-plan.md](../description/late-chunking-experiment-plan.md).

---

## Варианты

**Вариант А: документо-уровневый Late Chunking (jina-embeddings-v3, long-context)**
- Плюсы: полный контекст документа доступен каждому чанку
- Минусы: замерено на CPU (изолированный venv) — RSS при инференсе 3.5–4.5 ГБ (у E5-large ~2 ГБ), латентность в 3–11× выше E5. На проде 8 ГБ RAM всего, уже занятых Qdrant/FastAPI/реранкером/MCP — риск OOM. **Отклонён на этапе ресёрча, до реализации.**

**Вариант Б: Local Late Chunking — пулинг в масштабе parent-чанка**
- Идея: один forward pass на parent (E5-large, тот же embedder, что и сейчас), не на весь документ — окно 512 токенов E5 примерно совпадает с размером parent'а. Child-векторы — усреднение под-диапазонов токенов внутри этого forward pass.
- Плюсы: не меняет модель, эффект только на индексации (эмбеддинг запроса не меняется), архитектурно совместим с текущей Parent-Child схемой
- Минусы: требует token-aware parent-сплиттера (символьный лимит 2000 ненадёжен — 14.7% реальных parent'ов vault'а превышали 512 токенов E5, максимум 1316), требует обхода `store.add_texts()` при индексации (нет группировки child→parent в стандартном `Embeddings`-интерфейсе)
- **Реализован полностью и прогнан на реальных данных** (см. ниже).

**Вариант В: не трогать текущую схему, искать улучшения в другом месте (например, калибровка порога, per-source лимит, LLM-форматтер контекста)**
- Плюсы: ноль риска, можно начинать сразу
- Минусы: сам по себе не даёт ответа, было ли узкое место именно в отсутствии кросс-child контекста

---

## Решение

**Вариант Б реализован и проверен end-to-end — прирост качества не подтверждён, в прод не идёт.**

### Что сделано

Ветка `experiment/late-chunking` (не смержена): span-инструментация чанкера (`retriever/chunker.py`), обогащённый golden set (24 кейса на реальных данных vault'а вместо устаревших плейсхолдеров, 65 verbatim-цитат), span-based метрики (`eval/span_metrics.py`, без LLM — сравнение по символьным диапазонам), токен-aware parent-сплиттер, сама механика пулинга (`retriever/late_pooling.py`), интеграция в индексатор и раннер сравнения (`eval/compare_splitters.py`), систематическое хранение результатов (`eval/results_store.py`, `eval/results/runs.jsonl`).

### Результат прогона (24 кейса, честное сравнение — score-порог отключён у обеих стратегий одинаково, иначе порог, откалиброванный под naive-эмбеддинги, нечестно фильтрует late_pooling)

| Стратегия | Span Recall | Span Precision |
|---|---|---|
| naive_current (текущая прод-схема) | 0.544 | 0.063 |
| late_pooling (Local Late Chunking) | 0.543 | 0.074 |

Разница в пределах шума. Попарно по кейсам: win=3, loss=2, tie=16 (из 24). На retrieval-сложном подмножестве (multi-hop/paraphrase-кейсы, специально подобранные под гипотезу о кросс-child контексте) — смешанный результат (2 win/1 loss/2 tie), не «заметный прирост», как требовал заранее согласованный критерий принятия.

**Критерий решения** (согласован до прогона): внедрять при заметном приросте на сложном подмножестве и отсутствии регрессии >2 п.п. на полном сете. Ни одно условие для внедрения не выполнено — решаем не мержить.

### Побочные находки, которые пережили эксперимент

1. **`search.dense_score_threshold=0.84`** — фиксированный порог, откалиброванный под distribution похожести naive-эмбеддингов. Late-pooling-векторы систематически дают чуть более низкий абсолютный score при той же ранжировке (усреднение по контексту «размывает» пик похожести) — прямое A/B двух embedding-схем с одним фиксированным порогом методологически некорректно, нужно либо отключать порог для сравнения, либо перекалибровывать под каждую схему отдельно.
2. **Recall на уровне child систематически пессимистичен относительно того, что реально видит LLM** — child ищет точно, но одного «выстрелившего» child'а достаточно, чтобы весь parent (с недостающими фрагментами) попал в контекст. На реальном прогоне (`parent_child_prod_baseline`, `run_id=3d9efae8c19e`, честный прод-порог `0.84`): child-level span_recall=0.275, parent-level span_recall=0.341. Это официальный текущий бейзлайн ретривера — от него отталкиваемся при будущих попытках улучшить retrieval (например, порог `0.84` был откалиброван под старый, ныне удалённый golden set — есть подозрение, что он избыточно строг для актуального, более разнообразного набора вопросов).

## Последствия

- Прод не тронут: `IngestConfig.child_embedding_strategy` по умолчанию `"naive"`, `parent_split_by_tokens` по умолчанию `False` — эксперимент нигде не активирован вне tmp-коллекций.
- Ветка `experiment/late-chunking` не мержится в `main`.
- Инфраструктура эксперимента самостоятельно полезна независимо от исхода и может быть перенесена в `main` отдельным решением:
  - `retriever/chunker.py` — span-инструментация (`extra_metadata.span_start/end` у каждого чанка), не зависит от стратегии эмбеддинга, полезна для любых будущих правок retrieval
  - `eval/span_metrics.py`, `eval/results_store.py`, `eval/compare_runs.py` — детерминированная, дешёвая (без LLM) оценка retrieval-качества + систематическое хранение истории замеров
  - Обогащённый `eval/golden_set.yaml` (24 кейса на реальных данных, включая multi-hop/paraphrase/negative) — держится вне git (`.gitignore`, содержит личные/корпоративные данные владельца vault'а); пример структуры — `eval/golden_set.example.yaml`
- Новый официальный бейзлайн для будущих улучшений ретривера: `parent_child_prod_baseline` (`run_id=3d9efae8c19e` в `eval/results/runs.jsonl`) — child recall=0.275, parent recall=0.341, реальный прод-порог 0.84.
- Следующий кандидат на исследование, подсказанный побочными находками: пересмотреть калибровку `dense_score_threshold` под текущий (переписанный) golden set — старое значение `0.84` подбиралось под golden set, который сейчас удалён как нерабочий (ссылался на несуществующие файлы).
