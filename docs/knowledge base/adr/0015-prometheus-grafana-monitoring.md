## ADR-0015: Мониторинг на Prometheus/Grafana (расходы, задержки, fallback)

**Статус:** принято

**Дата:** 01.07.26

---

## Контекст

После перехода на общий LLM-шлюз ([[0014-llm-gateway]]) появилась инфраструктура,
за которой нужно наблюдать, но никакого мониторинга, кроме встроенного в LiteLLM не было:

- Расходы на LLM-запросы (по ключам, моделям, провайдерам) были видны только
  через ручной просмотр `LiteLLM_SpendLogs` в UI шлюза — неудобно смотреть
  динамику, искать пиковые дни, сравнивать ключи между собой
- Задержки (latency) веб-приложения RAGv2 и самого LLM-шлюза нигде не
  агрегировались — узнать, что стало медленнее, можно было только вручную
  дёргая эндпоинты или читая логи
- Не было видно, срабатывает ли fallback между провайдерами (OpenRouter ↔
  nano-gpt) — единственная причина завести fallback была надёжность
  ([[0014-llm-gateway]]), но без наблюдаемости невозможно проверить, что он
  вообще работает
- Ресурсы хоста (`192.168.3.160`, CPU/RAM/диск) и самого приложения
  (RPS, ошибки 5xx) не отслеживались — узнать о деградации можно было
  только когда пользователь уже заметил проблему

На домашнем сервере уже был отдельный LXC с Prometheus (`192.168.3.125`),
используемый для других целей — вопрос был не «разворачивать ли
мониторинг», а «на чём» и «что именно снимать».

---

## Варианты

**Вариант А: Ничего не делать, смотреть руками**

Смотреть `LiteLLM_SpendLogs` и логи контейнеров вручную по мере необходимости.

- Плюсы: ноль дополнительной инфраструктуры и работы
- Минусы: не видно исторической динамики (когда именно был всплеск
  расходов); нельзя сравнить провайдеров/ключи/модели за период; нет
  единого места для алертов в будущем; fallback остаётся «чёрным ящиком»

**Вариант Б: Prometheus/Grafana на существующем LXC 192.168.3.125 (принято)**

Использовать уже развёрнутый Prometheus как единую точку сбора метрик со
всех компонентов (хост RAGv2, приложение, LLM-шлюз), визуализация — в
Grafana.

- Плюсы: не нужно поднимать новую инфраструктуру — Prometheus уже есть и
  используется для других проектов; pull-модель Prometheus не требует
  изменений в момент сбоя источника (просто пропущенный scrape); Grafana
  даёт гибкие дашборды (per-key, per-model, per-provider срезы) без
  написания кода; PromQL позволяет считать production-метрики (`increase`,
  `histogram_quantile`) без дополнительного ETL; LiteLLM уже умеет отдавать
  метрики в формате Prometheus (`callbacks: ["prometheus"]`) — не нужно
  ничего допиливать на стороне шлюза
- Минусы: нужно поддерживать exporter-ы (node_exporter, cAdvisor) на хосте
  RAGv2; cAdvisor на LXC не различает Docker-контейнеры по имени (видит
  только systemd cgroups) — точечная детализация по контейнерам недоступна;
  Prometheus — ещё одна система, которая может быть недоступна (в этом
  случае просто нет свежих данных, без потери работоспособности самого
  RAGv2)

**Вариант В: SaaS-мониторинг (Datadog, Grafana Cloud и т.п.)**

- Плюсы: managed-инфраструктура, не нужно ничего поддерживать самому
- Минусы: платно; отправка метрик (в т.ч. потенциально чувствительных —
  расходы, ключи) во внешний сервис; на домашнем сервере с ограниченными
  ресурсами (8 ГБ RAM) нет причин платить за managed-решение, когда уже
  есть свой Prometheus

---

## Решение

Выбираем **Вариант Б**: используем существующий Prometheus/Grafana на
`192.168.3.125` как единую систему мониторинга для RAGv2 и LLM-шлюза.

Реализовано в два этапа:

**Этап 1 — экспортёры и scrape-таргеты:**

- `node_exporter` (хост RAGv2, `192.168.3.160:9100`) — CPU/RAM/диск/сеть
- `cAdvisor` (`192.168.3.160:8081`) — метрики на уровне cgroup
- `prometheus-fastapi-instrumentator` в `interfaces/web/app.py` — RPS,
  latency, статус-коды веб-приложения на `/metrics` (`192.168.3.160:8080`)
- `callbacks: ["prometheus"]` в LiteLLM (`litellm_config.yaml`) — расходы,
  латентность, количество запросов на `/metrics/` (`192.168.3.203:4000`)
- 4 новых scrape-джоба в `/etc/prometheus/prometheus.yml` на
  `192.168.3.125`: `ragv2_node`, `ragv2_containers`, `ragv2_app`,
  `litellm_gateway` (с `bearer_token_file` для авторизации к LiteLLM)

**Этап 2 — дашборды Grafana** (созданы напрямую через Grafana MCP,
`docs/grafana/*.json` — копии для истории):

- **RAGv2 / LLM Platform** (`ragv2-llm-platform`) — RPS/latency/ошибки
  веб-приложения, LLM latency/spend/запросы по клиентам шлюза, ресурсы
  хоста (CPU/RAM/диск). Row «Контейнеры Docker» убрана — cAdvisor на LXC
  не даёт разбивку по контейнерам, панели дублировали row «Хост»
- **LiteLLM / Использование моделей** (`litellm-usage-models`) —
  накопительные и дневные расходы по ключам (`api_key_alias`), расходы по
  моделям и провайдерам, дневное количество запросов по ключам, ошибки
  деплойментов и распределение успешных ответов по `api_base` как прокси
  для проверки fallback

**Важная оговорка про fallback:** LiteLLM не отдаёт отдельную метрику
«сработал fallback». Наблюдаемость собрана из двух связанных сигналов:
`litellm_deployment_failure_responses_total` (ошибка провайдера — именно
она запускает cooldown и переключение роутера) и
`litellm_deployment_success_responses_total` с лейблом `api_base`
(показывает, какой backend реально ответил). Если у модели `gpt-4.1-mini`
появляется успешный ответ с `api_base`, отличным от основного OpenRouter —
это и есть индикатор сработавшего fallback.

## Последствия

- Расходы, латентность и нагрузка теперь видны исторически — можно найти
  конкретный день с пиковым расходом у ключа, сравнить провайдеров и
  модели между собой, без захода в UI LiteLLM
- Работоспособность fallback ([[0014-llm-gateway]]) стала проверяемой
  (через ошибки деплойментов + распределение по `api_base`), а не
  предполагаемой
- Появилась зависимость на доступность `192.168.3.125` для *просмотра*
  метрик — но не для работы самого RAGv2 или шлюза (Prometheus только
  читает `/metrics`, ничего не проксирует и не блокирует)
- Ограничение: cAdvisor на LXC `192.168.3.160` не различает Docker-контейнеры
  по имени — если понадобится точная детализация ресурсов по контейнерам,
  потребуется либо мигрировать на полноценный хост, либо использовать
  `docker stats`/сторонний exporter вместо cAdvisor
- Следующий шаг — алертинг (Alertmanager) на превышение бюджета по ключу,
  рост latency, всплеск ошибок 5xx/деплойментов; на текущий момент
  дашборды только визуализируют, без уведомлений
- Трейсинг отдельных запросов реализован отдельно в [[0016-langfuse-tracing]]
  (self-hosted Langfuse) — Prometheus/Grafana закрывают только агрегированные
  метрики, не позволяют посмотреть конкретный запрос целиком
