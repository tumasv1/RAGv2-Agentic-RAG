## ADR-0014: Переход на общий LLM-шлюз (LiteLLM Proxy)

**Статус:** принято

**Дата:** 30.06.26

---

## Контекст

До этого решения `core/llm_client.py` обращался к LLM-провайдеру напрямую —
один провайдер (OpenRouter, модель `openai/gpt-4.1-mini`), один ключ в `.env`.

Это давало две проблемы:

1. **Надёжность.** Если провайдер перестаёт отвечать (dpi-блокировки, лимиты, авария,
   таймаут) — у агента нет fallback, запрос просто падает. Для агента,
   который должен быть доступен и пользователю в браузере, и потенциально
   Telegram-боту, это слабое место.
2. **Унификация.** У пользователя несколько независимых LLM-инструментов
   (RAGv2, агент на openclaw/DeepSeek, боты, n8n).
   Каждый инструмент по отдельности хранит свои ключи провайдеров, сам
   реализует (или не реализует) fallback, и нет единого места посмотреть
   сколько потрачено суммарно по всем инструментам.

Нужно было решить: реализовывать fallback-логику внутри `core/llm_client.py`
точечно для RAGv2, или вынести её на уровень инфраструктуры, общей для всех
LLM-инструментов.

---

## Варианты

**Вариант А: Fallback внутри RAGv2**

Реализовать в `core/llm_client.py` ручной fallback: при ошибке от основного
провайдера — повторить запрос через запасной ключ/провайдер.

- Плюсы: ничего нового не разворачивать, изменения только в одном проекте
- Минусы: код fallback/retry пришлось бы писать и поддерживать в каждом
  LLM-инструменте отдельно (RAGv2, openclaw-агент, будущие боты) —
  дублирование; нет единого учёта расходов; нет балансировки нагрузки между
  провайдерами; ключи провайдеров остаются размазаны по `.env`-файлам разных
  проектов

**Вариант Б: Общий LLM-шлюз — LiteLLM Proxy на отдельном LXC (принято)**

Вынести маршрутизацию, fallback и балансировку на уровень инфраструктуры:
отдельный сервис на LXC, к которому ходят все LLM-инструменты пользователя
по OpenAI-совместимому API.

- Плюсы: fallback и балансировка реализованы один раз в шлюзе, а не в каждом
  клиенте; единая точка учёта расходов (`LiteLLM_SpendLogs`) по всем
  инструментам и провайдерам; ключи провайдеров живут только на шлюзе —
  клиенты получают virtual key с бюджетом/лимитами, не видят реальных
  ключей; мультитенантность из коробки (Teams → Keys → Budgets); клиенту
  для подключения нужно поменять только `base_url`/`api_key` — код вызова
  LLM не меняется (OpenAI-совместимый протокол)
- Минусы: новая инфраструктура для обслуживания (LXC, Docker, Postgres,
  Redis); RAGv2 теряет немного в задержке (один лишний HTTP-хоп до шлюза);
  шлюз — новая точка отказа для *всех* LLM-инструментов одновременно (если
  упадёт сам шлюз — упадут все клиенты, не только RAGv2)

**Вариант В: Готовый SaaS-шлюз (OpenRouter как единственный провайдер,
без своего LiteLLM)**

OpenRouter сам по себе уже умеет роутить между моделями нескольких
провайдеров.

- Плюсы: ничего разворачивать не нужно
- Минусы: это не fallback между независимыми аккаунтами/провайдерами,
  которые уже были у пользователя (OpenRouter и nano-gpt — разные сервисы
  с разными ключами и тарифами); нет единого учёта расходов по *всем*
  инструментам пользователя, а не только тем, что идут через OpenRouter;
  нет мультитенантности/virtual keys для разделения по проектам

---

## Решение

Выбираем **Вариант Б**: разворачиваем LiteLLM Proxy как самостоятельный
проект `/Users/mikhail/Projects/LLM-gateway`, на отдельном LXC `10.0.0.20`
(Proxmox), доступ только по LAN.

Ключевая мотивация — две цели из контекста решены архитектурно, а не кодом:

- **Надёжность** → `router_settings.fallbacks` в шлюзе: если все deployment-ы
  модели недоступны/упали — переключение на запасную модель. Внутри одной
  логической модели (`gpt-4.1-mini`) уже два независимых deployment-а
  (OpenRouter + nano-gpt) с `routing_strategy: usage-based-routing-v2` —
  балансировка нагрузки между ними, не только реакция на сбой.
- **Унификация** → один шлюз, один адрес (`10.0.0.20:4000`), один формат
  учёта расходов для всех текущих и будущих LLM-инструментов. RAGv2 —
  первый клиент, дальше: openclaw/DeepSeek-агент, Telegram-бот, n8n.

Реализация в RAGv2:

- `core/config.py::GatewayConfig` (`enabled`, `base_url`, `model`) +
  `gateway_api_key` (виртуальный ключ, не реальный ключ провайдера)
- `core/llm_client.py::get_llm()` — при `gateway.enabled=True` идёт на шлюз;
  `False` — fallback на прямой вызов `LLM_PRIMARY_*` (аварийный путь мимо
  шлюза, например если шлюз недоступен)
- `.env`: только `GATEWAY_API_KEY` (virtual key проекта `ragv2` с бюджетом
  и rpm-лимитом) — реальные ключи OpenRouter/nano-gpt в RAGv2 больше не
  хранятся

На шлюзе:

- Каталог моделей управляется через UI (`store_model_in_db: true`), не
  файлом
- `gpt-4.1-mini` — два deployment-а (OpenRouter, nano-gpt), балансировка +
  fallback между ними
- Virtual key `ragv2` — бюджет $5/мес, лимит 200 rpm, доступ только к
  `gpt-4.1-mini`

## Последствия

- RAGv2 больше не хранит ключи провайдеров — только виртуальный ключ шлюза
  с ограниченным бюджетом
- Откат на прямой вызов провайдера — одна строка конфига
  (`gateway.enabled: false`), без правки кода
- Шлюз стал общей инфраструктурой — изменения в нём (новые модели, цены,
  fallback-цепочки) видны сразу всем клиентам, а не только RAGv2
- Появилась новая зависимость: если LXC `10.0.0.20` недоступен (сеть,
  перезагрузка хоста) — RAGv2 теряет LLM, пока не включат
  `gateway.enabled: false` вручную. Нет автоматического fallback «шлюз
  недоступен → прямой вызов провайдера»
- Учёт расходов теперь смотрят на шлюзе (`LiteLLM_SpendLogs`), не в RAGv2
- Наблюдаемость метрик шлюза (`/metrics`) реализована в
  [[0015-prometheus-grafana-monitoring]]; трейсинг отдельных запросов —
  в [[0016-langfuse-tracing]]
