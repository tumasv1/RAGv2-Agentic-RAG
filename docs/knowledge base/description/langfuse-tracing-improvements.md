Анализ от 02.07.26, после первичного запуска Langfuse (Этап 3). Цель — сделать
трейсы удобными для анализа: и для RAGv2, и для остальных клиентов LiteLLM-шлюза
(OpenClaw, Speech2Text, будущие боты/n8n).

## Проблема 1 — двойной учёт RAGv2 🔄 (код готов, ждёт деплоя и проверки на проде)

Один вопрос агенту порождает **два независимых семейства трейсов**: `LangGraph`
от CallbackHandler в графе и отдельные `litellm-acompletion` от шлюза на каждый
LLM-вызов того же диалога. Они не связаны, и **стоимость считается дважды**:
генерация `ChatOpenAI` в LangGraph-трейсе (~$0.000938) и та же генерация
`litellm:Ragv2` в трейсе шлюза (~$0.000641). Итог: расходы в дашбордах Langfuse
для RAGv2-трафика завышены ~вдвое, список трейсов замусорен (1 вопрос = 2–4 записи).

**Решение:** LiteLLM поддерживает проброс `trace_id` от клиента — RAGv2 передаёт
`langfuse_trace_id` в `metadata`/`extra_body` запроса к шлюзу, и генерация шлюза
ложится **внутрь того же трейса**, что и дерево графа. Один вопрос — один трейс:
и структура ReAct, и реальный `api_base` провайдера в одном месте.

**Реализация** (проверена эмпирически на живом шлюзе, litellm 1.89.2 + langfuse SDK 4.x):
- `agent/graph.py::_langfuse_span()` — корневой спан через
  `start_as_current_observation` (v4 API; `start_as_current_span` был в v3) вокруг
  `graph.ainvoke()` в `ask()`/`ask_debug()` — даёт ambient OTEL-контекст;
- `core/llm_client.py::get_langfuse_extra_body()` — достаёт trace_id текущего
  спана (сначала тихо проверяет OTEL-контекст, чтобы вне спана не сыпался
  "Context error" в лог) и собирает `extra_body.metadata.existing_trace_id`;
- `agent/nodes.py` — `agent_node`/`generate_node` передают extra_body в
  `invoke()`; LangChain доносит его до тела запроса (проверено);
- `existing_trace_id` выбран вместо `trace_id`: семантика «добавь генерацию,
  не перезаписывая атрибуты трейса» — владелец трейса остаётся граф RAGv2.
- Контекст пробрасывается и в sync-ноды (LangGraph копирует contextvars в
  executor-поток — проверено).

## Проблема 2 — session_id не используется ⬜ (приоритет: высокий, дёшево)

В Langfuse есть вкладка **Sessions**: трейсы с одним `session_id` группируются
в «диалог». Сейчас `session_id` пуст у 100% трейсов, при этом `thread_id` RAGv2
уже есть в каждом трейсе — но закопан в metadata, где по нему нельзя ни
группировать, ни фильтровать.

**Решение:** передавать `thread_id` как session_id — в `agent/graph.py` в config
графа добавить `metadata={"langfuse_session_id": thread_id}`. Многоходовые
диалоги станут читаться целиком.

## Проблема 3 — клиенты шлюза различаются плохо и неконсистентно ⬜ (приоритет: высокий, дёшево)

Сейчас определить «чей трейс» можно тремя частичными способами:

- Тег `RAGv2` — есть только у запросов RAGv2 (задан в метаданных его virtual key);
  у OpenClaw аналогичного тега нет, только `User-Agent: OpenAI/JS 6.39.1`.
- Имя генерации `litellm:OpenClaw` / `litellm:Ragv2` — надёжно, но видно только
  внутри трейса; в списке всё — `litellm-acompletion`.
- Тег провайдера (`Openrouter`) — есть у RAGv2, нет у OpenClaw. Полезен для
  проверки fallback: при переключении на nano-gpt тег сменится.

**Решение:** в `litellm_settings` шлюза добавить `langfuse_default_tags` с
`user_api_key_alias` (алиас ключа → тег на каждом трейсе автоматически, включая
будущих клиентов) и `cache_hit`. Плюс выровнять метаданные существующих ключей
(OpenClaw, Speech2Text) по образцу RAGv2.

## Проблема 4 — dev и prod пишут в одну кучу ⬜ (приоритет: средний, дёшево)

Локальные прогоны с Mac и прод-трафик неотличимы — поле environment пусто у всех
трейсов, статистика расходов/латентности смешивается.

**Решение:** `LANGFUSE_TRACING_ENVIRONMENT=production` в `.env` на проде RAGv2 и
на шлюзе, `development` — локально. В UI появится фильтр окружения.

## Проблема 5 — имена и input трейсов неинформативны ⬜ (приоритет: средний)

- Все трейсы графа называются `LangGraph`, все трейсы шлюза — `litellm-acompletion`.
  В списке из сотни трейсов нужный не найти глазами.
- Input LangGraph-трейса — 14 КБ: полный SYSTEM_PROMPT + история; вопрос
  пользователя тонет. В списке первое видимое — одинаковый у всех системный промпт.

**Решение:** в `ask()` задавать имя/input трейса явно (имя = первые слова вопроса,
input = сам вопрос) через `propagate_attributes`/`update_current_trace` из
langfuse SDK. Для клиентов шлюза — `metadata.generation_name`/`trace_name` в запросе.

## Проблема 6 — служебные вызовы неотличимы от основных ⬜ (приоритет: средний)

- Вызовы `generate_title` (TITLE_PROMPT) уже видны в трейсах шлюза и выглядят
  как ответы агента.
- Будущие eval-прогоны (RAGAS, 18+ вопросов за раз) зальют проект неразмеченными
  трейсами.
- Смежная дыра: **RAGAS-судья ходит в OpenRouter напрямую** (`RAGAS_JUDGE_API_KEY`),
  мимо шлюза — его расходы не видны нигде (ни LiteLLM, ни Langfuse, ни Grafana).

**Решение:** отдельные virtual keys на шлюзе (`ragv2-title`, `ragv2-eval`) — даёт
сегментацию и по расходам LiteLLM, и по тегам Langfuse автоматически (после п. 3).
Судью RAGAS перевести на шлюз — закроет последний неучтённый LLM-трафик.

## Мелочи ⬜ (приоритет: низкий)

- **user_id** пуст везде — станет актуально с Telegram-ботом (вкладка Users).
- **Шумовые спаны** `tools_condition`/`check_iteration_limit` (1 мс) — обвязка
  LangGraph; вреда мало, убирать сложно, игнорировать.
- **Ретенция ClickHouse**: трейсы копятся бесконечно (диск LXC — 20 ГБ). Поставить
  retention в Langfuse (Settings → Data Retention), например 90 дней — синхронно
  с решением «ClickHouse не бэкапим».
- **`RuntimeError: cancel scope...`** в логах прод-приложения после первого
  запроса — разово, ответ и трейс не пострадали; если участится — копать отдельно
  (тот же класс asyncio-проблем, что и известные MCP-гочки).
