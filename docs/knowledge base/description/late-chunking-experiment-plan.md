# План: эксперимент Local Late Chunking

Документ дизайна эксперимента (research/design doc) — фиксирует контекст, гипотезу и поэтапный план проверки. Код в рамках создания этого документа не писался; реализация — отдельная последующая работа по фазам ниже.

## Контекст (почему это делаем)

Текущая Parent-Child схема чанкинга (ADR-0010): child-чанки (800 симв., overlap 300) ищутся, parent-чанки (2000 симв.) отдаются LLM. Children эмбеддятся независимо друг от друга — attention внутри модели не выходит за границы одного child'а, поэтому анафоры и смысловые связи внутри секции/parent'а (например, «он», «этот проект», «с кем был разговор») могут теряться при векторизации отдельного маленького куска, если сам child их не содержит явно.

Обсуждали переход на Late Chunking (Jina AI): сначала эмбеддим текст целиком, потом усредняем токен-векторы по границам чанков — то есть чанки получают вектора, «знающие» более широкий контекст через двунаправленный attention.

**Что уже исследовано и отвергнуто:** документо-уровневый Late Chunking требует long-context модель (jina-embeddings-v3, окно 8k). Замерено на Маке (изолированное окружение, torch==2.5.1 + transformers==4.49.0, CPU 4 потока): модель грузится нормально, но во время инференса RSS взлетает до 3.5–4.5 ГБ (у E5-large — ~2 ГБ), а латентность в 3–11× выше (запрос: 576 мс против 51 мс; полный документ: 2563 мс против 301 мс). На проде — 8 ГБ RAM **всего**, уже занятых Qdrant/FastAPI/реранкером/MCP. Риск OOM и деградации отклика чата неприемлем. **Документо-уровневый Late Chunking на jina-v3 исключён из рассмотрения.**

**Найдена жизнеспособная альтернатива:** окно E5-large (512 токенов) примерно соответствует размеру одного **parent-чанка** (2000 символов). Значит, late-chunking пулинг можно делать в масштабе parent'а, а не всего документа — без смены модели, без риска по памяти/латентности (эмбеддинг запроса не меняется вообще, эффект только на индексации).

Важный нюанс, найденный при замере на реальном vault (431 файл, 1337 parent-чанков): char-лимит `parent_chunk_size=2000` — ненадёжный прокси токен-лимита. Медиана — 307 токенов, но **14.7% parent'ов уже сейчас превышают 512 токенов**, максимум — 1316 токенов (2.5× лимит). Соотношение токен/символ у русского текста нестабильно (0.26–0.66 в выборке) в зависимости от плотности текста. Значит, нужен токен-aware, а не символьный сплиттер для parent-уровня — это отдельная, обязательная часть эксперимента, без которой пулинг будет молча (или не молча) обрезать часть parent'ов.

**Ещё один нюанс:** сейчас только **children** получают префикс с метаданными файла (`_build_child_prefix()` в `retriever/chunker.py`) перед эмбеддингом — **parent** хранится без префикса вообще (он собирается на лету только для показа LLM, в эмбеддинге не участвует). Если при пулинге просто взять «голый» parent, получится регресс относительно текущей схемы. Решение: добавлять префикс **один раз в начало parent-текста** перед прогоном через модель — тогда через bidirectional attention каждый child, пулящийся из этого parent'а, впитает влияние метаданных файла в свои контекстуализированные векторы (даже не включая сами токены префикса в диапазон усреднения). Это сильнее, чем текущее буквальное дублирование строки в каждый child.

## Термин: что именно тестируем

**Local Late Chunking** — late-chunking пулинг в масштабе **parent-чанка** (не всего документа). Один forward pass на parent (с гарантированным помещением в 512 токенов E5 за счёт токен-aware сплиттера) → усреднение под-диапазонов токен-векторов → вектор каждого child'а. Children в рамках одного parent'а получают общий контекст; между разными parent'ами — по-прежнему нет (как и сейчас, смягчается overlap'ом parent'ов в 200 символов).

## Цели / не-цели

**Цели:**
- Полностью обратимый, изолированный эксперимент — прод не трогаем ни на каком этапе.
- Новая инфраструктура оценки (span-based recall/precision по цитатам golden set), которая переживёт этот конкретный эксперимент и пригодится для будущих правок retrieval.
- Количественное сравнение baseline vs Local Late Chunking на копии vault (`/Users/mikhail/Documents/Obsidian/ОсновноеRAGAS`) и расширенном golden set.

**Не-цели (сознательно за скобками):**
- Документо-уровневый Late Chunking на jina-v3 или другой long-context модели — отклонено по замерам памяти/латентности; отдельный возможный будущий ресёрч, если этот эксперимент покажет, что именно кросс-parent контекст — узкое место.
- Изменение прод-конфига, прод-коллекции Qdrant или поведения по умолчанию — все новые флаги по умолчанию выключены.
- Комбинация «Late Chunking children → отбор Parent'ов» — отложена до результатов этого эксперимента.

## Фазы

### Фаза 0 — Ветка и флаги
- Создать `experiment/late-chunking`.
- Новые поля `IngestConfig` (`core/config.py`):
  - `child_embedding_strategy: Literal["naive", "late_pooling"] = "naive"`
  - `parent_split_by_tokens: bool = False`
  - `parent_max_tokens: int = 440` (бюджет с запасом: `"passage: "` + спецтокены ≈5–6, контекстный префикс ≈10–25 в зависимости от тегов)
- `config.yaml` не меняется — дефолты сохраняют прод-поведение.

### Фаза 1 — Инструментация span'ов в чанкере (нужна независимо от исхода эксперимента)
Файл: `retriever/chunker.py`
- При построении parent'ов из нормализованного текста файла — запоминать `(doc_start, doc_end)` каждого parent'а. При построении children из текста parent'а — вычислять их `(doc_start, doc_end)` через смещение на `parent.doc_start`.
- Хранить как `extra_metadata={"span_start": int, "span_end": int}` в `ChunkMetadata` (`core/types.py`) — переиспользуем существующее свободное поле, без миграции схемы; никто из потребителей (`search.py`, `formatting.py`, `agent/tools.py`) не завязан на состав `extra_metadata`, риск нулевой.
- Вынести нормализацию текста файла (`_extract_frontmatter` + `_normalize_wikilinks`) в публичную функцию `normalize_document_text()`, переиспользуемую и в чанкере, и в скрипте извлечения цитат (Фаза 2) — чтобы offsets и цитаты считались по идентичному тексту.
- Это всегда-включённое, дешёвое изменение — не зависит от `child_embedding_strategy`, полезно для любых будущих правок retrieval.

### Фаза 2 — Обогащение golden set
Файлы: `eval/golden_set.yaml` (расширение) + новый `eval/extract_reference_quotes.py`
- +6 retrieval-сложных кейсов: multi-hop (ответ размазан по ≥2 документам), парафразы без «жёстких терминов» для BM25 (чтобы эффект был виден именно на dense-поиске), 1–2 негативных.
- Новое поле у кейса: `reference_quotes: [{doc: str, quote: str}]`.
- Скрипт: для каждого `reference_docs` кейса — загрузить и нормализовать текст (`normalize_document_text()` из Фазы 1) → LLM (переиспользуем `eval.metrics.setup_ragas_judge_llm()` — тот же OpenRouter gpt-4o-mini, что уже используется как надёжный судья с JSON-выводом, а не основной gateway) извлекает цитаты, отвечающие на вопрос → verbatim-валидация (`quote in normalized_text`, иначе retry/флаг на ручную правку).
- Обязательная ручная вычитка всех 24 кейсов перед использованием как ground truth.

### Фаза 3 — Span-based метрики
Новый файл: `eval/span_metrics.py`
- `span_recall(reference_quotes, doc_text, retrieved_spans) -> float` — доля символов цитаты, покрытая объединением retrieved-диапазонов.
- `span_precision(...)` — обратная метрика (доля retrieved-текста внутри золотых диапазонов).
- Подключение в `eval/runner.py::run_golden_set` — берёт spans из `result.metadata.extra_metadata["span_start"/"span_end"]`.

### Фаза 4 — Токен-aware parent-сплиттер
Файл: `retriever/chunker.py`
- При `cfg.ingest.parent_split_by_tokens=True`: `length_function` для parent-уровня `RecursiveCharacterTextSplitter` считает токены E5-токенизатора (`context_prefix + text`) вместо символов, цель — `parent_max_tokens`.
- Валидационный скрипт: прогнать `chunk_file()` по всему dev-vault, проверить, что **максимум** (не p99!) токенов на parent строго < 512. Пока не будет 0 превышений — Фаза 5 не начинается.

### Фаза 5 — Реализация пулинга (Local Late Chunking)
Новый файл: `retriever/late_pooling.py`
- Функция: на вход — сырой текст parent'а, его children (с локальными char-границами внутри parent'а), строка префикса → на выход — `dict[child_chunk_id, vector]`.
- Механика: прямой `transformers.AutoTokenizer`/`AutoModel` (в обход обёртки `sentence-transformers`, нужен доступ к `last_hidden_state` + offset mapping), токенизация `"passage: " + prefix + "\n" + parent_text` — **отдельно проверить эмпирически, нужен ли токен-префикс `"passage: "` вообще при таком способе использования модели, не предполагать заранее**. Один forward pass → для каждого child'а усредняем токены в его (сдвинутом на длину префикса) диапазоне → L2-нормализация (как делает `sentence-transformers` внутри, `normalize_embeddings=True`).
- Вектор самого parent'а — не меняется, эмбеддится как раньше (`store.embeddings.embed_documents([parent_text])`): parent'ы сейчас не участвуют в поиске по вектору (`retriever/search.py::_dedup_and_fetch_parents` достаёт их по ID, не по similarity), так что точность этого вектора не влияет на retrieval.
- Индексация: новая функция `_index_files_late_pooling()` в `retriever/indexer.py` (параллельно текущей `_index_files()`), в обход `store.add_texts()` (её интерфейс `Embeddings.embed_documents()` получает плоский список текстов без информации о группировке по parent'ам — не подходит для пулинга). Вместо этого: dense-вектора считаем через `late_pooling`, sparse — как сейчас через `FastEmbedSparse` (BM25-текст child'а с префиксом не меняется), затем `store.client.upsert()` напрямую с `PointStruct`, используя уже существующие константы полей из `retriever/search.py` (`_DENSE`, `_SPARSE`, `_CONTENT_KEY`, `_META_KEY`) вместо новых магических строк.
- `_index_files()` выбирает naive/late_pooling путь по `cfg.ingest.child_embedding_strategy`.

### Фаза 6 — Раннер эксперимента (переиспользуем `compare_splitters.py`)
Файл: `eval/compare_splitters.py` (расширение, не замена)

- Добавить стратегию `late_pooling` (`parent_split_by_tokens=True`, `child_embedding_strategy="late_pooling"`, размеры child'ов не меняются — меняется только способ эмбеддинга).
- `_index_strategy()` уже временно подменяет `cfg.ingest.*` и восстанавливает в `finally` — расширить на новые поля по тому же паттерну.
- Для span-метрик нужны и parents, и children с одной tmp-коллекции — добавить `make_search_detail_fn(collection_name)` в `retriever/search.py`, зеркало уже существующего `make_search_fn()`, но возвращающее `(parents, children)` как `search_with_detail()` (переиспользует уже параметризованные по `store` `_search_children`/`_dedup_and_fetch_parents`).
- Предварительно: `docker compose up -d qdrant` (см. гарантии выше).

Если прирост слабый/неоднозначный — эксперимент закрывается без мержа, фиксируем результат в этом документе.

## Результаты (Фаза 8, прогон 2026-07-08)

Все 8 фаз реализованы на ветке `experiment/late-chunking` и прогнаны end-to-end на полном golden set (24 кейса) против реального dev-vault (`ОсновноеRAGAS`, 431 файл).

### Найденная методологическая проблема: фиксированный score-порог

Первый прогон (smoke-test, 3 кейса) показал резкий провал late_pooling (span_recall 0.33 против 0.87 у naive). Расследование показало: `search.dense_score_threshold=0.84` в `config.yaml` откалиброван под распределение похожести naive-эмбеддингов. Прямая проверка на кейсе "Сколько детей у сотрудника Х" (id 1):

| Стратегия | Score корректного чанка |
|---|---|
| naive | 0.8430 (едва проходит порог 0.84) |
| late_pooling | 0.7984 (тот же чанк, тот же ранг #1 — но ниже порога, полностью отфильтрован) |

Late-pooling-векторы систематически дают чуть более низкий абсолютный cosine similarity к запросу (ожидаемо — усреднение по более широкому контексту "размывает" пик похожести), при этом ранжирование (какой чанк лучше) не деградирует. Фиксированный порог, откалиброванный под одну схему эмбеддинга, делает A/B-сравнение с другой схемой методологически некорректным.

**Для честного сравнения финальный прогон на 24 кейсах выполнен с `dense_score_threshold=0` и `sparse_score_threshold=0`** (порог отключён у обеих стратегий одинаково) — сравнивается чистое качество ранжирования, а не взаимодействие ranking-качества с порогом, откалиброванным под другую схему.

### Итоговые метрики (24 кейса, порог отключён)

| Стратегия | Чанков | Время индексации | Span Recall | Span Precision |
|---|---|---|---|---|
| naive_current (текущая прод-схема, 800/300) | 5088 | 1375 сек | 0.544 | 0.063 |
| late_pooling (Local Late Chunking, 800/300) | 6561 | 944 сек | 0.543 | 0.074 |

RAGAS-метрики и LLM-судья (confirmatory-слой) недоступны в этом прогоне — OpenRouter (`ragas_judge_*`) вернул 403 Access denied (сетевая проблема окружения на момент прогона, не связана с экспериментом). Прогон не упал благодаря try/except в `_evaluate_strategy` — сигнал для решения даёт span-based слой, как и планировалось (RAGAS/judge — confirmatory, не основной).

Попарное сравнение по кейсам (`python -m eval.compare_runs 7dfd7d5f882b b0dfd23b3c3a`): **win=3, loss=2, tie=16** (3 кейса пропущены — негативные/цитата не нашлась в обоих). На retrieval-сложном подмножестве (кейсы 5, 19, 20, 21, 22 — multi-hop и paraphrase, Фаза 2): 2 win (19: КУ multi-hop, 22: курсы-парафраз), 1 loss (5: 2Л multi-hop), 2 tie (20, 21) — смешанный результат, не «заметный прирост».

Побочное наблюдение: индексация late_pooling заметно быстрее (944 сек против 1375) — совпадает с ожиданием из ресёрч-фазы (один forward pass на parent вместо N частично перекрывающихся forward pass'ов на children).

Ряд кейсов (9, 13, 15, 16, 17, 18, 20) дали span_recall=0.0 у **обеих** стратегиях одинаково — это не деградация late_pooling, а ограничение самого eval-харнесса: `run_golden_set`/`search_detail_fn` вызывают поиск в чистом dense-режиме без извлечения BM25-термов, а часть этих кейсов (например, id 18 — точный редкий алфавитно-цифровой код тикета) специально требует лексического, а не семантического поиска. Не влияет на честность сравнения (одинаково для обеих стратегий), но искусственно снижает средний span_recall относительно того, что реально видит прод (там `bm25_terms` извлекает агент).

### Решение

**Критерий решения** (согласован заранее): внедрять, если Span Recall показывает заметный прирост на retrieval-сложном подмножестве, и ни одна метрика на полном сете не просела более чем на ~2 п.п.

- Регрессии на полном сете нет (Δ span_recall = −0.002, span_precision = +0.011 — в пределах шума).
- Заметного прироста на сложном подмножестве нет (смешанный результат 2/1/2).

**Эксперимент закрыт без мержа в прод.** Local Late Chunking в текущей реализации (пулинг в масштабе parent-чанка, ~800/300 children) не даёт статистически значимого улучшения retrieval-качества на этом vault'е и golden set, при этом даёт быструю индексацию. Гипотеза о том, что кросс-child контекст внутри parent'а — заметное узкое место текущей Parent-Child схемы, не подтвердилась на этих данных.

Ветка `experiment/late-chunking` не мержится. Инфраструктура, созданная в рамках эксперимента (span-инструментация чанкера, `eval/span_metrics.py`, `eval/results_store.py`, `eval/compare_runs.py`, обогащённый `golden_set.yaml` с 65 verbatim-цитатами, токен-aware parent-сплиттер), — самостоятельно полезна независимо от исхода этого конкретного эксперимента и может быть перенесена в `main` отдельным решением, если понадобится для будущих правок retrieval.

### Что стоило бы попробовать дальше (не сделано в рамках этого прогона)

- Перекалибровать `dense_score_threshold` отдельно под late_pooling (а не просто отключать) — возможно, при правильном пороге прирост в precision (+0.011 уже виден даже без калибровки) станет более выраженным.
- Прогнать сравнение в гибридном режиме (dense+BM25), а не dense-only — устранит искусственный 0.0-recall у BM25-специфичных кейсов и даст более репрезентативную картину прод-поведения.
- Больше кейсов на retrieval-сложном подмножестве (5 кейсов — маленькая выборка, результат 2/1/2 статистически не значим).
